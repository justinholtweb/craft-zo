What syncs

Money moves
both ways

Money moves in more than one direction, and the books have to show all of it.

  • An existing Zoho contact is adopted, never duplicated
  • Invoices are promoted out of draft, so receivables are real
  • A refund is a credit note — Zoho cannot refund a paid invoice

Tax

Decide who
wins on tax

Commerce calculates tax. So does Zoho. They will not always agree — so Zo makes it a choice instead of a surprise.

  • A custom adjuster is included without Zo modelling it
  • Every mode is measured, not assumed
adjustment
= paid
No rates sent. The difference goes on as one adjustment, so the total matches to the cent.
mapped
Zoho
Line items carry tax ids and Zoho computes. Itemised tax reports, variance measured.
none
0.00
No tax anywhere. Only sensible for a tax-exempt store.

The default is adjustment — because an invoice that disagrees with the payment is a problem you find at year end.

Idempotency

One invoice,
however hard
you try

A queue retry, a redelivered webhook, an impatient second click — all of them find the first attempt’s row and stop.

Unique index on (type, craftKey)
1Claim the link firstInsert the row before a single byte is sent
2A duplicate key is the answerNot an error to handle — the second attempt has found the first
3Send, then record what came backZoho’s id and number land on the row that was claimed
One code path. It cannot create two.
